# Security foundation and boundaries

Map position has an independent five-second diagnostic freshness check. Stale, missing, future-dated, invalid or disconnected positions are not shown as live markers; this does not establish positioning accuracy, other measurement freshness, vehicle identity or physical safety. Heartbeat and map-position expiry use in-memory elapsed time; other telemetry freshness and age displays still use wall-clock timestamps and may be affected by clock changes. See [Phase 92](phase-92-report.md) and [Phase 93](phase-93-report.md).

The optional minimum-overlap calculation uses volatile user assumptions and gives advisory ideal spacing only; it neither changes the overlap setting nor proves physical coverage. See [Phase 91](phase-91-report.md).

The optional sideways-error margin uses volatile user-entered assumptions only; it is not a sensor measurement, safety check or physical coverage guarantee. It does not change missions, network behavior or hardware commands. See [Phase 89](phase-89-report.md).

The local coverage estimate can retain up to 16,384 gap sample centers per preview and render them on the existing map; they are volatile and neither a mission nor an observation of worked soil. Map styles can still contact the already configured provider. See [Phase 86](phase-86-report.md).

## Implemented

- `AuthorizationPolicy` is deny-by-default for missing, blank, disabled or expired sessions. Its role matrix is policy groundwork; only local account administration and saved UDP peer configuration currently consume the policy. It does not grant a vehicle-control capability.
- First-run local administrator setup, password sign-in, sign-out, administrator-created Operator/Viewer accounts, account enable/disable, and a 15-minute in-memory session. Each login receives a new session identifier; requests from an earlier session cannot authorize a later login for the same account. Expiry updates the UI with a timer and is rechecked on foreground entry after device sleep and at account-action boundaries. Sessions are cleared when the app process restarts.
- A signed-in user can change their own password by providing the current password. Wrong current-password attempts share login throttling. The password change preserves account identity and role, generates a new salt/verifier, writes the account change and audit event together, and requires another sign-in. Permissions are rechecked after password derivation.
- Login issues a session only after its audit write succeeds. Logout and password change revoke the current session before persisting their changes. Storage failures clear privileges and preserve the stored data for recovery; coroutine cancellation is propagated and submitted password arrays are cleared, including when cancellation occurs while waiting for an account transaction.
- Passwords are not stored. Each account has a random salt and a PBKDF2-HMAC-SHA256 verifier (600,000 iterations). Credential derivation runs away from the UI thread; the UI clears its password fields after submit.
- The bounded local account and audit database is encrypted using AES-GCM and a non-exportable Android Keystore AES key, with the app package name as authenticated additional data. If the key/data cannot be opened, the app preserves existing data and reports the failure instead of silently resetting it.
- Five consecutive failed sign-ins trigger a 60-second lockout. The monotonic lockout is reset after a detected device reboot. Audit is encrypted at rest, capped at 500 events, and the UI displays the newest 30.
- Current audit events: initial admin setup, successful/failed login, logout, session expiry, successful/failed password change, account creation, enable/disable, and authorized UDP endpoint-change requests. It is device-local and **not** tamper-evident; it does not record vehicle commands or prove who physically used the device. A verified login can have a success audit entry even if cancellation prevents the session from being issued afterward.
- Only an authenticated, enabled, unexpired administrator can save or clear the UDP endpoint. A changed peer is exposed for opening only after authorization, its request audit and the preference write succeed. Open is disabled during the save. A previously saved peer can still be opened for read-only monitoring without sign-in. Transport receive and dashboard browsing remain available while signed out.
- Account lists and audit history are published only to administrator sessions. Other signed-in users see their own account; signed-out UI state contains neither the account list nor audit history.
- Backup is disabled and app data-extraction rules exclude the app data. Device migration, root compromise and compromised app processes remain outside this protection boundary.
- A pure `DriveSafetyGate` lists the required evidence for eventual control admission. The checks default to unsatisfied and are not populated from trusted providers. All vehicle commands and the emergency-stop action remain unavailable.

## Not implemented / not a security claim

Local app accounts are not an organization identity system and do not pair or authenticate the Cube Orange, BLE radio, VESC or rover. Local credentials protect only this installation's account database and administrator-only local actions; they do not encrypt telemetry or authenticate the network peer. Forgotten-password reset, administrator recovery, multiple-admin provisioning, encryption-key rotation, audit export, tamper evidence and remote policy management are not implemented.

Operator and Viewer roles exist, but role permissions for movement, missions, spray, hydraulics and diagnostics are not connected to command boundaries because those commands and subsystem adapters do not exist. The current app remains monitoring-only. Hiding or disabling a control in Compose is not authorization; any future actuator command must re-check a trusted session and its permission at the command/use-case boundary.

`usesCleartextTraffic=false` does **not** encrypt or authenticate UDP or MAVLink. A fixed UDP peer filters accidental traffic but cannot prove peer identity against spoofing. MAVLink CRC detects corruption, not forgery. Unsigned HEARTBEAT is liveness only; signed frames are rejected because no signing-key verifier is provisioned. No MAVLink command sender, replay defense, reconnect service, authenticated radio profile or physical failsafe verification exists. Receive-age labels are not subsystem health.

Bluetooth discovery and the selectable GATT-notification receiver can inspect an identified BLE device and parse incoming MAVLink bytes. Phase 17 additionally receives MAVLink 2 through an explicitly selected, already-paired Classic SPP radio using secure RFCOMM. Android pairing and secure RFCOMM do not establish a trusted rover identity or authorize vehicle commands. Classic has no application-byte transmit path, closes on app backgrounding and shares the exclusive telemetry ownership gate with UDP/BLE. The actual Cube Orange → installed radio → physical phone path and the radio's identity, security mode and reliability have not been verified. VESC telemetry may use a different protocol and is not decoded by either MAVLink receiver.

No offline map-region downloader, background communication service, secure vehicle pairing, mission transfer/execution, physical emergency-stop validation, deadman, link-loss command behavior, actuator integration, release signing setup or production qualification is provided. Do not use this build to operate machinery; use the rover's independent physical safety system.

## Lifecycle and storage

Phase 76 adds an offline coverage preview in the local planner. Current outline coordinates and bounded width/overlap strings enter a pure local-plane geometry calculation (64 vertices, 2 km extent, 500 passes maximum) on a background dispatcher. Input/outline changes cancel work and clear old results; no stale result is retained as current. Results are volatile and never enter a route repository, export, vehicle telemetry or command admission. Invalid geometry and over-budget requests fail visibly. Displayed tool strips are ideal, clipped rectangles; they do not establish obstacle clearance, physical coverage, survey accuracy or safe turns. No new permission, dependency, credential or network route is introduced.

Phase 77 adds a bounded local headland width and conservative boundary clearance. This reserves a visual boundary band rather than establishing physical turn clearance or coverage; the headland itself is not planned. Untrusted values and outlines remain bounded and failures are displayed. No data persistence or command authority is added.

Phase 78 adds 128 × 128 bounded cell-center sampling for approximate unplanned main area and reserved-headland area, separately, on the existing background preview path. No interior samples means estimates unavailable; none detected is not a zero-gap claim. No error bound, physical soil measurement, persisted result or command authority is inferred. Calculation remains bounded by field and pass limits and canceled work cannot publish stale results.

Phase 79 counts definitely/possibly classified grid cells to show modeled-area ranges. Uncertain boundary/strip cells widen the upper bounds; the ranges are subject to floating-point and geometric-model assumptions and are not field-survey, safety, physical coverage or command evidence. No new persistence, dependency or external authority is added.

Phase 80 compares two independent bounded local coverage calculations with identical inputs. The in-memory cards show failure independently and changes clear old results; no automatic choice, route write, network transmission or vehicle-command permission follows. Calculation can take up to twice the existing bounded preview work, and canceled work may run until it returns but cannot publish stale results.

Phase 81 lets the user explicitly project one successful comparison's local pass endpoints back to geographic coordinates for a separate volatile planning-map source. Date-line-crossing fields are rejected because the existing field-outline rendering/fit behavior is not verified there. Edits, recomputation and hide clear the source; the cyan lines are labeled centerline previews. Style reload reapplies the currently selected overlay. No mission/draft write, new endpoint, permission, dependency or command authority is added. The existing configured map provider may still receive normal basemap requests.

Phase 50 parses checksum-valid MAVLink `RADIO_STATUS (109)` into a separate radio-only result and retains one latest field sample plus a count in the current in-memory diagnostic session. It is never a vehicle message, autopilot selection, heartbeat/RC evidence, command authorization, persisted record or telemetry-report export. Raw RSSI/noise scales are device-specific; CRC is not source authentication. A new session clears the observation, and a closed-session display remains labelled historical. Physical Cube-heartbeat delivery is still unverified.

Phase 23 retains only six numeric AUTOPILOT_VERSION metadata fields and a local receipt timestamp in session memory. UID/UID2, custom version bytes and capability flags are not retained in decoded/domain state. The existing selected-autopilot source filter applies; unsigned metadata is not authenticated hardware identity or command authorization. A disconnected observation is labeled historical and a new session clears it. The telemetry report allowlist is unchanged and does not export the new fields. No request, firmware update or configuration write is sent.

Phase 22 adds a second bounded in-memory parameter snapshot and an exact-text comparison. Neither snapshot enters vehicle state, command authorization or safety evaluation. There is no merge/apply/export of file contents; missing entries receive no inferred defaults. Import errors retain the previous pair, cancellation/generation checks prevent superseded publication, and removing the reference never deletes the source file. Both fingerprints identify file bytes, not vehicle identity or trustworthy configuration.

Phase 21's RC/PWM monitor receives only from the existing selected autopilot source. Its raw inputs/outputs are observations, not motor identities, physical output measurements or safety evidence. Values are hidden when link/heartbeat/sample freshness is missing; the five-second display window is not a failsafe. Session restart clears samples; at most four output ports are retained. No command, calibration or stream-rate request is sent. Telemetry report export includes their receipt times only, excluding raw RC/PWM values and RSSI.

Phase 45 adds a separate yes/no `RC_CHANNELS` receipt observation to the Classic checklist and explicit Classic evidence report. It requires the current Classic session, fresh heartbeat, selected-source accepted-message observation and fresh RC state; it does not authenticate the sender or prove the SBUS lead, stick movement, neutral position, stopping ability or control permission. No raw RC values are added to that report.

Phase 20 permits explicit export of a previewed, allowlisted telemetry evidence snapshot through Android's document picker. It excludes coordinates, track, device addresses/names, network endpoints, accounts, parameters and raw messages. Capture/session times and observed MAVLink source IDs remain included. Saved reports are not encrypted by the app and may be uploaded by a chosen cloud document provider. There is no automatic report transmission or raw-packet logging. A failed/interrupted export may leave a partial file; the user must inspect it before sharing.

Phase 19 adds receive-only MAVLink 1 compatibility to the same message allowlist. MAVLink 1 has no signing support; accepting it does not establish trust. Version counters describe decoded frames, including source-filtered messages, not an authenticated or negotiated peer protocol. MAVLink 2 signed candidates remain rejected. No transmit, automatic protocol negotiation or rover configuration changes are introduced.

Phase 18's parameter-file review treats the selected document as untrusted, bounded text. The in-memory snapshot is separate from live vehicle state, account roles and drive admission; it cannot apply parameters or satisfy a safety check. A SHA-256 file fingerprint is provenance assistance, not authentication. No URI permission is persisted and no file content is uploaded or saved by this feature. Failed imports retain the prior snapshot with a visible warning. The selected document provider may itself use cloud storage; importing through it is subject to that provider's behavior.

Compose renders immutable state and callbacks; it does not open sockets. Hilt ViewModels own screen actions; repository storage uses application context and DataStore. The local access provider holds the current session in memory and closes it on process restart. The existing app still has one active vehicle state, not a multi-vehicle session manager. There is no background service or automatic socket reconnect.

The local access database uses Android Keystore AES-GCM and Android's `PBKDF2WithHmacSHA256` provider. The KDF setting follows OWASP's current PBKDF2-HMAC-SHA256 recommendation; device performance and the final release security configuration still need review. Android Keystore protects key extraction, not a compromised unlocked device or process. See [Android Keystore](https://developer.android.com/privacy-and-security/keystore), [Android cryptography guidance](https://developer.android.com/privacy-and-security/cryptography), and [OWASP Password Storage Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html).
