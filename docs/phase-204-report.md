## Design and execution path

The Classic, BLE, TCP or UDP receive flow still passes chunks to `MavlinkSession`, then `MavlinkParser`, source selection and `MavlinkDiagnosticsAccumulator`, then the repository and `ConsolePanels.mavlinkDiagnostics`. The parser now remembers only the claimed end of a rejected candidate during bytewise resynchronization. A later invalid-CRC candidate starting within that span is marked as overlapping; the cumulative total remains unchanged. The panel displays overlapping and complementary outside-span counts, existing unsupported-ID/flag counts, and the number of bytes currently held for an incomplete candidate. A chunk split is not a rejection. New fields are bounded, volatile and reset with the session/parser; no raw frames, addresses, endpoints, coordinates or history are added. See D-204-01.

The claimed span is unverified. An overlapping CRC failure may still represent actual corrupt data, and an outside-span failure can still be a false start. Neither count is a packet-loss rate or a safety verdict. The app's CRC, payload, signed-frame, source-selection, heartbeat, transport and command policies are unchanged. The new rows are screen diagnostics only; the existing explicit telemetry report format is unchanged.
