# Phase 42 — serial byte-signature diagnosis

## Reason

The October bench screenshots showed an open Classic SPP socket and 120,221 received bytes but zero validated supported MAVLink messages. CRC-failure and unsupported-ID candidate counts could be generated by a stream that is not MAVLink. Before changing Cube or radio settings, an operator needs a narrower, read-only observation of what reaches the phone.

## Change

The current receive session counts raw `0xFE` (MAVLink 1 start) and `0xFD` (MAVLink 2 start) bytes across all incoming chunks. The decoder screen and the explicit Classic/telemetry evidence reports show the aggregate counts. A new session resets them. No raw bytes, device addresses or payloads are retained for this feature.

If bytes arrive with neither marker and no supported message validates, the app suggests checking the serial forwarding format. If markers appear but no supported message validates, it suggests checking framing and routing. These are diagnostics, not a hardware fault verdict: arbitrary non-MAVLink data can contain either byte, and a marker alone does not establish a valid frame or a Cube connection.

The app does not change telemetry rates, serial parameters, receiver binding or wiring. It does not transmit data, arm, move, or stop the rover. RC & PWM still requires a validated Cube heartbeat and `RC_CHANNELS` before it can display inputs.

## Bench check

With motors/ESC outputs physically isolated and the T12/R12/Cube powered, connect the identified T12 Classic device in **Application settings → Bluetooth / HC-05**. In **Analyze telemetry → Link & messages**, observe input bytes, raw start-byte counts and decoded supported messages over the same current session. If input increases but decode remains zero, capture the Classic evidence report for the hardware team. Check the separate R12 UART ↔ Cube TELEM1 telemetry path and settings against the accepted parameter-file baseline; SBUS → RCIN alone cannot carry MAVLink telemetry back to the app. Do not change wiring or parameters based only on marker counts.

## Validation

The combined working tree passed 370 JVM unit tests with zero failures. `assembleDebug` and Android UI-test source compilation also passed; the UI tests were not run on a device. `lintDebug` passed with zero errors and 32 warnings. Unit tests cover counting across chunks, empty input, session reset, screen guidance and aggregate report content. This phase has no physical link acceptance until the bench retest confirms actual checksum-validated Cube messages and later `RC_CHANNELS` values. Commands remain unavailable.
