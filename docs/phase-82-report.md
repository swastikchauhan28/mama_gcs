# Phase 82 — Coverage selection through the offline map

Date: 2026-10-27. User approved an end-to-end emulator test. Baseline `d18b7f00972e0f6df2bef66cc6073b1300815761`, clean worktree. Model/version unavailable. See [D-082-01](DECISIONS.md#d-082-01-exercise-coverage-selection-through-the-native-map).

## Scope and verification

The test uses MissionScreen with a synthetic rectangle, in-memory draft and callbacks, and a temporary local MapLibre style. It selects each direction in the real comparison UI and checks native source geometry, containment and orientation, rendered cyan pixels, invalidation on edit and absence of mission callbacks. Portrait and landscape are separate fresh fixtures. No production behavior, persistence, dependency, external destination or hardware command is changed. The tests do not establish actual soil coverage, geodetic accuracy, implement behavior or hardware safety.

Initial build and lint succeeded (most tasks including JVM and lint report were up-to-date). Initial emulator run `app/build/acceptance-20261027-173146-fc3d0fb9/` failed both orientations on a 30-second source-feature count timeout. The original synthetic field straddled the equator and prime meridian, coinciding with native tile boundaries, and the query preceded Fit draft. The exact cause was not observed because the test did not include the returned count. The revised fixture avoids those boundaries, fits before querying, and reports the actual geometry on timeout; the direction, count, containment and rendered-pixel assertions are retained. Existing real-basemap and physical acceptance gaps remain open.

The second run `app/build/acceptance-20261027-173701-9bd04bcb/` failed in both orientations: native source queries returned the same five line geometries twice. Coordinates were also quantized by roughly 5e-8 degrees at the boundary. The test counts distinct geometries and allows 1e-7 degrees (about 1.1 cm here) for native tile quantization; it still requires five or ten distinct lines, containment, correct direction and visible pixels.

The final emulator run passed 2/2 with a healthy Android gate; evidence is `app/build/acceptance-20261027-174129-0f1f7a93/`. Both directions were verified through the real planner screen in each orientation, including expected distinct counts, containment, orientation, cyan pixels at a projected line center and clearing after overlap changes. The draft remained equal and the action list empty. The portrait map is removed on clear; landscape also checks the native source becomes empty. Four screenshots are under `app/build/phase82-{portrait,landscape}-{north,east}.png`; portrait north/east and landscape east were visually inspected. GPU launch mode was unavailable. This checks one synthetic rectangular field with an offline style; other field shapes and actual basemap/physical accuracy remain separate acceptance gaps.

Visual review identified two pre-existing usability concerns: in portrait the map controls partly obscure the field after Fit draft, and the settings summary's single-preview direction can differ from the selected comparison overlay direction (the latter has its own selection status). These were not changed in this test-only phase and merit a separate UI decision.
