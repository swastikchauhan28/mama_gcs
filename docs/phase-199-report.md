# Phase 199 — Speed receive evidence

Date: 2026-11-18. Baseline: clean `main` at `ae3a70b`. The user approved a bounded read-only diagnostic after Phase 198's speed-card clock fix. Model/version unavailable.

## Goal, path and decision

The detailed Analyze telemetry speed card previously showed only the first unavailable reason. It could not show, at the same instant, whether the selected-autopilot heartbeat or `GLOBAL_POSITION_INT` speed sample had aged out. `MavlinkSession` and `VehicleRepositoryImpl` already store both elapsed receive timestamps in volatile `VehicleState`; `RoverSpeedMonitorPanel` samples elapsed time; `RoverSpeedMonitor.assess` decides availability; the detailed `RoverSpeedPanel` renders it. The new assessment carries two `SpeedReceiptEvidence` records, each with a bounded enum status (`NOT_RECEIVED`, `INVALID_TIME`, `FRESH`, `STALE`) and a non-negative age in milliseconds when the timestamp is valid. The same clock sample supplies the speed gate and both displayed ages. The records are computed on display, not persisted or transmitted; the compact Operate card does not grow.

The two failures are named together when both expire. A degraded/disconnected vehicle still hides numeric speed. Its receipt rows can show recent incoming packets with `LINK NOT CONFIRMED`; this describes app receipt, not a healthy link. A first intermediate version hid the ages as `LINK CLOSED`. Live observation showed that the transport may continue delivering position packets during heartbeat loss, so that label was replaced. Decision D-199-01 records the alternatives and corrections. The five-second limit, selected source, parser/source filtering, command boundary, dependencies, permissions and external destinations did not change.
