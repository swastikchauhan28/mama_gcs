# Phase 196 — Classic checklist clock alignment

Date: 2026-11-17. Baseline `9b9b740` on `main`. The worktree already contained the uncommitted 2026-11-17 T12_485 live-test notes in `docs/HANDOVER.md`, `docs/hardware-integration.md`, and `docs/bluetooth-live-check-2026-11-17.md`; this change preserves them. The user approved the bounded checklist fix and a read-only phone retest. Model/version unavailable.

## Symptom, path and decision

During an open Classic session with T12_485, the checklist displayed waiting for bytes or heartbeat not confirmed while the same app session counted current Classic input and displayed a recent accepted autopilot heartbeat in Link & messages. `ClassicBluetoothScreen` recomposes on vehicle updates but passed its one-second `produceState` tick as the elapsed-time boundary to `ClassicConnectionCheck.assess`. A newly received byte or message could carry an elapsed timestamp after that cached tick. The domain check correctly rejects future timestamps, so the UI clock caused it to reject an otherwise current receipt. See decision `D-196-01` in `DECISIONS.md`.

The screen now samples `SystemClock.elapsedRealtime()` when it evaluates the checklist and keeps the one-second tick to refresh idle display state. The helper takes the later of the tick and sampled clock. No transport, decoder, stored data, permission, dependency, network or command path changed. The domain check still requires the active Classic session, current-session receipt timestamps, a five-second window and an accepted heartbeat from the selected autopilot. The input is an untrusted serial stream; passing this display check does not authenticate the remote or prove RC, vehicle safety, or sustained connection.
