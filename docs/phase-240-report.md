## Goal and scope

They approved the material change to the previously receive-only Classic write boundary on 2026-11-27. Baseline: `224099c6bf137920be3682ce4c0d32c63ad78730`, with unrelated untracked `output/` demo artifacts. AI model/version unavailable. No Cube or radio was connected for this software phase.

## Design and trust boundary

The existing Classic session remains the sole selected telemetry owner. The Android RFCOMM adapter now exposes its output stream only to `BluetoothTransport`; generic `VehicleTransport.send` still throws. `sendCorrection` accepts a defensive-copy, CRC-checked `Rtcm3Frame`, encodes only MAVLink 2 `GPS_RTCM_DATA` (233), serializes fragments and writes them to the same selected socket. The Classic view model checks a current selected-autopilot heartbeat received after that socket opened and no older than five seconds before opening the caster and before each correction. Optional VRS GGA additionally requires current-session, fresh Cube GPS. The URL and credentials are session-only, masked in the prompt and excluded from state, logs and records. HTTP remains an explicit per-session opt-in. Stop, lost link/heartbeat and app backgrounding close the caster. No parameter, arm, mode, mission, motor or generic send path was added.

The caster and radio are external, unauthenticated inputs relative to physical Cube identity. RTCM CRC and MAVLink framing reject corruption but do not prove caster quality or that T12/R12 forwards the outbound bytes. One caster, a 256 KiB/min input limit and the existing 720-byte RTCM frame limit apply. A slow or failed radio write ends that NTRIP attempt; Android socket closure is the recovery path. The user must reconnect manually. No new dependency, manifest permission, stored credential or migration was added.
