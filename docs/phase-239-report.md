## Decision before implementation · 2026-11-26

The owner requested RTK/GPS injection like Mission Planner and explicitly approved a first stage limited to a user-entered HTTPS NTRIP caster, the app's existing direct TCP Cube link, and outbound MAVLink `GPS_RTCM_DATA` (233). Baseline `998a9b6d963898ed7a9b08d0d53873187b843c5d`. Older untracked `output/` artifacts are unrelated. AI model/version unavailable.

The existing app is receive-only: `TcpTelemetryViewModel` owns `TcpTransport`, which rejects generic `send`; `MavlinkSession` accepts only selected-autopilot receive messages. The new path is explicit operator start → HTTPS caster → bounded RTCM3 frame validation → MAVLink 2 message 233 fragmentation/CRC → the same active TCP socket. It cannot send arming, mode, mission or actuator messages. No Cube parameter or motor output is changed by the implementation or simulated tests. The operator's caster credentials remain memory-only and never enter logs or app preferences. GPS coordinates are not sent to the caster; NTRIP mountpoints requiring GGA remain unsupported in this stage.

Protocol references: [ArduPilot RTK correction overview](https://ardupilot.org/copter/docs/common-rtk-correction.html), [MAVLink GPS_RTCM_DATA definition](https://mavlink.io/en/messages/common.html#GPS_RTCM_DATA), and the generated [message 233 layout/CRC header](https://raw.githubusercontent.com/mavlink/c_library_v2/master/common/mavlink_msg_gps_rtcm_data.h). The message header specifies a 180-byte data field and CRC extra 35; the fragmentation flags are defined in the MAVLink message description.

Alternatives: generic `VehicleTransport.send` would undermine the existing command boundary; adding Bluetooth and UDP at once would broaden physical paths without link-specific evidence; using plain HTTP would expose caster credentials; forwarding raw unvalidated RTCM would pass corrupt or oversized frames. Choose a TCP-only, HTTPS-only, typed correction method with fail-closed framing, bounded buffers, no redirect and explicit start/stop. This adds an external destination chosen by the operator and permits one outbound MAVLink message, so the approval was specifically requested and received. Revisit Bluetooth, GGA, credential persistence and live Cube acceptance in separate scoped work.

## Implementation and verification · 2026-11-26

`Rtcm3Framer` accepts only complete CRC24Q-valid RTCM3 frames up to 720 bytes, the four-fragment MAVLink limit. The validated frame owns a defensive copy and returns copies to callers, so an accepted correction cannot be changed after validation. `MavlinkRtcmEncoder` emits only MAVLink 2 message 233 with CRC extra 35; its sequence/fragment flags are checked by JVM tests. `NtripHttpsClient` uses the platform TLS trust store, rejects redirects and keeps Basic credentials out of URLs. `TcpTransport.send` still throws; only `sendCorrection` writes the typed correction packets to the existing connected socket. The TCP view model requires a fresh selected-autopilot TCP heartbeat before starting and before each correction; backgrounding, disconnect and explicit Stop close the caster. One-minute input is capped at 64 KiB. The TCP screen has host/port/mountpoint/username/password fields, sent/rejected counters and Cube-reported GPS fix. No new dependency, manifest permission, stored secret or vehicle command sender was added.

The first focused JVM run found a wrong CRC24Q bit step and corrupt-frame resync bug; these were corrected without weakening the assertions. The corrected focused five tests passed (`app/build/phase239-focused-retry.txt`). The full software gate `./gradlew.bat :app:testDebugUnitTest :app:assembleDebug :app:assembleDebugAndroidTest :app:lintDebug --no-daemon --max-workers=1 --console=plain` passed (`app/build/phase239-full-gate.txt`): 97 tasks, 24 executed/73 up-to-date; 545 JVM tests, zero failures/errors/skips; lint zero errors/27 warnings.
